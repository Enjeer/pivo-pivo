# План разработки MVP

Все этапы после нулевого требуют одобрения владельца продукта по архитектурным решениям. Это план, не начало реализации.

## Этап 0 — исследование и архитектурное проектирование (текущий)

**Цель:** зафиксировать требования, выбранный стек, модель, интерфейсы, риски и этапы.

**Результаты:** этот набор документов.  
**Критерии приёмки:** семь документов согласованы; неподтверждённые возможности помечены; вопросов владельца продукта выделены отдельно.  
**Статус:** подготовлено, реализации нет.

## Этап 1 — доказательство картографической и источниковой пригодности

**Компоненты:** минимальный технический spike Flutter + выбранная карта/SDK; контрольный каталог заведений Минска; пробные запросы walking/driving/transit для ограниченного набора пар; ключи и квоты в тестовом проекте.

**Критерии приёмки:**
- проверить контрольный набор мест по районам и категориям, оформить точность/пустые результаты, а не только успешный статус;
- сравнить Android SDK отображение, поиск/детали и UX атрибуции;
- измерить ответы для выбранных режимов и времени суток; отдельно проверить многоточечный маршрут через плечи;
- проверить легальные ограничения хранения, атрибуции и кэширования;
- получить фактическую оценку расходов на прогнозируемую активность.

Без API ключей этот этап не может подтвердить доступность сервиса; отсутствие ключа/аккаунта фиксируется как блокер. Не генерировать массовые исходники.

## Этап 2 — доменное ядро и локальные данные

**Компоненты:** модели каталога/плана/сметы, функции бюджета и порядка остановок, SQLite-репозиторий для избранного/планов/заметок, базовая навигация Flutter.

**Критерии:** unit-тесты арифметики, валюты, unknown и участников; CRUD локальных данных; тест сохранения порядка; решение по защите заметок подтверждено платформенным тестом.

## Этап 3 — каталог и API

**Компоненты:** одно API каталога, схема данных и админский процесс импорта/проверки; viewport query, категории, пагинация, поиск, сообщения об ошибках.

**Критерии:** исходная выборка для MVP имеет документированное основание и даты проверки; bbox не возвращает весь город; внешние IDs и provenance сохранены; rate limit и валидация проходят интеграционные тесты.

## Этап 4 — карта, поиск и карточка

**Компоненты:** карта Минска, категории и фильтры, карточка, избранное, переход во внешнюю навигацию.

**Критерии:** карта/каталог имеют корректную атрибуцию; запросы ограничены видимой областью, debounce/cancel/pagination работают; плохая сеть и пустой результат представлены корректно; запрещённый API-кэш отсутствует.

## Этап 5 — маршрут и смета

**Компоненты:** редактор упорядоченных остановок, адаптер маршрутизации, способы движения, пользовательские оценки расходов, смета и остаток бюджета.

**Критерии:** маршрут рассчитывается по плечам; transit не притворяется единым многоточечным расчётом; такси неизвестно без данных; unknown не суммируется как ноль; переходы пешком/авто/общественный транспорт показывают источник, свежесть и ограничения.

## Этап 6 — журнал, приватность, доступность и надёжность

**Компоненты:** личные заметки/метки, системные напоминания только opt-in, защита локальной БД, доступность интерфейса, состояние повторного запроса.

**Критерии:** заметки остаются локальными, не появляются в логах/публичных endpoints; тестирование удаления/резервного поведения и системных разрешений; интерфейс проверен на доступность и разные размеры.

## Этап 7 — закрытая бета и решение о выпуске

**Компоненты:** Android release pipeline, crash/latency/usage metrics без личных данных, мониторинг квот/расходов, магазинные тексты и политика приватности.

**Критерии:** Android release собирается; основные сценарии проходят на реальном устройстве и слабой сети; нет критичных дефектов; API расход внутри лимита; источники и ограничения публично объяснены. iOS готовится после беты на macOS/Xcode и отдельной проверки карты.

## Тест-план сквозных сценариев

Покрыть: поиск, несколько фильтров, несколько остановок с изменением состава/порядка, варианты транспорта, unknown цен, смету на участника, заметку и приватность, провайдер offline. Unit-тесты домена отделены от API контрактных, интеграционных и UI-тестов. Ни один ответ стороннего API не должен подменяться фиктивным mock в production.
