# Решение по технологическому стеку

Статус: Flutter используется. Для MVP выбраны OSM/Overpass как источник POI и публичный FOSSGIS OSRM для пеших/автомобильных маршрутов; они подключены напрямую из клиента и не считаются production-SLA сервисами. Google Maps URLs остаются внешним fallback, не используется платный Places/Routes API. Полнота POI Минска и доступность Overpass не подтверждены.

## Рекомендация

**Flutter (Dart) для Android/iOS; OSM tiles + Overpass для ограниченной выборки POI; FOSSGIS OSRM для пешего/автомобильного маршрута; собственный backend и платные API пока не вводить.** Это обратимое MVP-решение для проверки сценария, не обещание полноты каталога или безотказной работы.

Фактическое MVP использует `flutter_map` для OSM-подложки, `OverpassPlaceCatalogRepository` для POI, `FossgisOsrmRoutingProvider` для маршрутов и `url_launcher` для универсальных ссылок Google Maps. Maps URLs не требуют API-ключа и не являются Places/Routes API; мобильные ссылки ограничены четырьмя плановыми точками. Избранное, план и заметки остаются локальными.

Flutter лучше соответствует заданной цели: Android-first, единые UI и доменная логика для iOS, быстрый выход на карты и доступ к нативным SDK через плагины/platform channels. Карта остаётся платформенной интеграцией, но не должна проникать в расчёты бюджета и планирования.

## Запись технического решения

- **Контекст и проблема:** нужно начать с Android, разумно переиспользовать UI и доменную логику на iOS, показать карту и маршруты Минска и не создавать зависимости от неподтверждённых данных.
- **Рассмотренные альтернативы:** Flutter; React Native с TypeScript; Kotlin Multiplatform с нативным или Compose Multiplatform UI. Для карт рассмотрены Google Maps Platform, Yandex MapKit, Mapbox и OSM-derived данные/хостинг.
- **Решение:** Flutter как мобильный стек; OSM выбран для подложки и временного POI-источника, Google Maps URLs — для внешней навигации. Google Maps Platform не подключена; каталог и доменная модель остаются независимыми от провайдера.
- **Преимущества:** единый UI и доменный код; одна основная технология на две платформы; OSM-derived data и роутер доступны без ключа/оплаты; интерфейсы каталога и маршрутизации позволяют сменить адаптер.
- **Недостатки:** риски поддержки Flutter-плагина карты; публичные OSM/FOSSGIS сервисы не дают SLA; полнота POI и локальное качество маршрутизации Минска не измерены; FOSSGIS не даёт transit и логирует координаты маршрута.
- **Последствия:** ограничивать область и частоту запросов, показывать атрибуцию и provenance, обрабатывать сбой без демо-fallback в live режиме; перед ростом проверить SLA/условия, контрольную выборку и необходимость собственного backend. Интегрированный транзит остаётся вне MVP.
- **Условия пересмотра:** плохое покрытие Минска, неприемлемый прогноз затрат, неподходящие условия оплаты/доступа, запреты хранения, нестабильность SDK либо подтверждённое преимущество Yandex/MapLibre на одинаковом контрольном наборе. React Native/KMP также пересматриваются, если команда/требование нативности меняются.

## Решение для MVP: каталог, маршруты и цены

- **Контекст:** приложению нужны реальные заведения для карты и маршруты по нескольким упорядоченным остановкам, но нельзя вводить платежи, ключи или обязательный backend без подтверждённой потребности.
- **Каталог — решение:** OSM POI через ограниченные viewport-запросы Overpass. OSM различает amenity-категории и может содержать имя, адрес, сайт, телефон, часы и кухню, но полнота тегов зависит от сообщества; OSM не подтверждает, что заведение открыто, и не даёт меню. Пользователь видит provenance и атрибуцию ODbL. Из полного Минска ничего не выгружается.
- **Маршрут — решение:** FOSSGIS OSRM, публичный маршрутизатор на OSM; поддерживает foot/car и несколько координат, но не общественный транспорт. Альтернатива Google Routes потребовала бы ключей, тарификации и отдельной проверки хранения; собственный OSRM потребовал бы инфраструктуры/обновления графа. В коде есть заменяемый `RoutingProvider`.
- **Цены — решение:** автоматический источник не выбран и не подключён. Google Places предоставляет сведения о местах, но не является каталогом актуальных цен меню; официальные меню требуют отдельного согласия/проверки условий для каждого источника. Запрещены массовый скрейпинг и выдача OSM/оценок за подтверждённые цены.
- **Ограничения/последствия:** публичный Overpass не имеет SLA; live-запрос из среды разработки завершился timeout, поэтому покрытие и работоспособность конкретного запроса не подтверждены. FOSSGIS ограничивает трафик максимум одним запросом в секунду, запрещает тяжёлое использование, логирует координаты и не гарантирует доступность. В клиенте добавлены ограничения площади/объёма/результатов для Overpass и последовательная отправка маршрутов с лимитом 1 запрос/с. Ошибки не заменяются фиктивными данными.
- **Когда пересмотреть:** при живом пилоте проверить категории/районы и долю пропусков. Перейти на управляемый источник или backend только при измеренном отказе/ограничении, росте трафика, нужде в контроле обновлений, пользовательских публикациях либо защищённых API credentials. Платный вариант требует отдельного согласования стоимости.

### Сравнение мобильных стеков

| Критерий | Flutter | React Native (TypeScript) | Kotlin Multiplatform |
|---|---|---|---|
| Повторное использование UI и логики | Высокое, один Dart-код для обоих приложений | Высокое для JS/TS и UI, часть нативных модулей остаётся платформенной | Высокое для домена/сети/данных; UI может быть общим через Compose Multiplatform или раздельным |
| Карты Android/iOS | Нужен поддерживаемый плагин либо нативный bridge; карта — особая зона интеграции | Зрелая экосистема, но карта также зависит от нативного модуля и версий платформ | Нативные SDK удобны по качеству интеграции, но разные Android/iOS UI и мосты усложняют кросс-платформенную карту |
| Цена/сложность команды | Один UI-стек и язык; найм Flutter-компетенций | Большой рынок TypeScript; React Native и нативные зависимости требуют дисциплины версий | Kotlin удобен Android-команде, но для качественной iOS-части нужны Kotlin и Swift/interop навыки |
| Тестирование домена | Чистые Dart-модули хорошо тестируются без SDK | Логика TS тестируема; состояние UI/нативные модули требуют интеграционных тестов | Общая логика тестируема; платформенные реализации проверяются отдельно |
| Поддержка и риск | Нужно следить за совместимостью Flutter-плагинов с Google/MapLibre SDK | Зависит от качества сторонних native modules и режима Expo/bare | Технология сильна для общего домена; полное общее UI — отдельное решение, не бесплатное свойство KMP |
| Сборка | Android SDK; iOS-сборка требует macOS/Xcode | Android SDK; iOS-сборка требует macOS/Xcode | Android SDK; iOS framework/Xcode требует macOS |

Официальные отправные точки: [Flutter platform channels](https://docs.flutter.dev/platform-integration/platform-channels), [React Native docs](https://reactnative.dev/docs/getting-started), [Kotlin Multiplatform](https://kotlinlang.org/docs/multiplatform/get-started.html), [Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API), [FOSSGIS routing usage policy](https://www.fossgis.de/arbeitsgruppen/osm-server/nutzungsbedingungen/). Ни один стек/провайдер сам по себе не решает полноту POI Минска или цены меню.

### Почему не React Native

Это жизнеспособная альтернатива, особенно при уже существующей TypeScript-команде, но в текущем пустом репозитории нет существующих React-компонентов для повторного использования. Сценарий с тяжёлой картой всё равно требует нативного bridge/плагина; преимущество знакомого веб-стека само по себе не компенсирует второй рантайм-интеграции карт. Пересмотреть выбор, если продуктовая команда уже использует React Native/TypeScript.

### Почему не Kotlin Multiplatform

Отлично подходит, если основная цель — общее доменное ядро при нативном UI и нативных картах, но заданная задача требует Android-first и повторного использования заметной части UI. KMP с Compose Multiplatform уменьшает этот разрыв, но добавляет решение о зрелости кросс-платформенного UI и интеграции карт. Пересмотреть, если важнее максимально нативный UI/SDK и есть сильная Kotlin/Swift-команда.

Разделять отображение карты, поиск/каталог POI, геокодирование и маршруты. Документы доказывают наличие функций продукта, но не полноту заведений/маршрутов конкретно в Минске. Эту полноту надо проверять на ограниченном наборе контрольных мест и реальных запросов.

| Google Maps Platform | Maps SDK; Places API с выборочными полями; Routes API, включая пешие/авто и `TRANSIT` | В актуальной таблице тарифа Maps SDK указано неограниченное бесплатное использование. Для Mapbox/Yandex также не использовать неподтверждённые ставки из сторонних обзоров.

## Источники данных по Минску: факты и неизвестное

- Официальная документация описывает Google Places Search/Details и Google Routes, но не гарантирует полноту POI Минска, актуальность конкретного заведения или доступность транзитных данных для каждого района/времени.
- Google Routes `TRANSIT` не принимает промежуточные waypoints. Для маршрута с несколькими остановками нужны отдельные запросы для каждого плеча (либо отдельный алгоритм), что влияет на стоимость, время ответа и смысл пересадок.
- Mapbox Directions подтверждает walking/drive/cycling, но не transit. В Mapbox Search Box подтверждён поиск POI; сохранение/кэширование должно соответствовать условиям конкретного endpoint.
- Yandex MapKit Free подтверждает отображение карт и маркеров с лимитом MAU, но в изученной странице не подтверждены нужные продукты для поиска и всех видов маршрута.
- OSM открытая база — возможная основа импорта по Минску, не гарантия актуальности и не источник меню/акций. Публичные OSM-сервисы нельзя использовать как массовый production backend.
- В официальных изученных материалах не найден API, который гарантировал бы меню, реальные цены/акции либо число свободных мест заведений Минска.

### Финансовое решение и контроль

До запуска ограниченного прототипа задать предельный месячный расход и проектные квоты. Не выдавать точную смету API без прогнозов MAU, открытий карты, поисков и плеч маршрутов. Считать отдельно map loads, Places-поля/SKU и маршрутные запросы; включить бюджетные уведомления, квоты и серверный rate limit. Не встраивать серверный ключ Routes в приложение. Клиентский ключ SDK ограничить bundle/application ID и подписью.

**Критерий пересмотра рекомендации:** если контрольные поисковые запросы и маршруты Минска показывают пробелы/неприемлемые цены или юридически несовместимые правила, сравнить Yandex и MapLibre/коммерческие OSM-тайлы по тому же тестовому набору и документировать отдельное решение до реализации интеграции.
